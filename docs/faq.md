# よくある疑問
{: .no_toc }

1. TOC
{:toc}

## Erlang や Akka は「1アクター = 1プロセス」ではないの？

用語の「プロセス」が何を指すかによります。

- **Erlang**: 論理的には1アクター = 1プロセスです。ただしそのプロセスは BEAM VM が自前で作る軽量プロセス（数KB）で、OS のプロセスでもスレッドでもありません。コア数ぶんのスケジューラスレッドが、数十万〜数百万のプロセスを切り替えて実行します
- **Akka**: アクターごとの実行単位はありません。アクターは「状態 + メールボックス + ハンドラ」のオブジェクトで、メッセージが来たときだけスレッドプールのスレッドを借りて実行されます

どちらも「多数のアクター : 少数の OS スレッド」です。違いは、アクターが自分のスタックを持つかどうかです。Rakka は Akka 型（スタックなし）です。

## それでも集約 = 1アクターなの？

はい。Akka Persistence も Erlang/Elixir の CQRS ライブラリ（Commanded など）も、集約1つにつきアクター1つが標準で、Rakka も同じです。1対1でないのは、アクターと実行単位（OS スレッドや Ractor）の関係のほうです。詳しくは [アクターと Ractor](concepts/actors-and-ractors.html) を参照してください。

## アクターの死活は管理していないの？

しています。Akka もアクターごとにスーパーバイザ階層・再起動・死亡監視を持っています。Erlang は VM レベルでプロセスが実際に終了し、Akka は例外を捕まえて状態を捨て、作り直すことで同じ意味論を実現しています。Rakka はアクター単位を Akka 式、シャード単位を Erlang 式（`Ractor#monitor`）で扱います。[障害処理](concepts/failures.html) を参照してください。

## アクターが Ractor でないなら、Ractor を使う意味はある？

あります。役割は「並列実行と隔離の強制」です。

- シャード同士は GVL に縛られず、1プロセスの中で複数コアを使う
- Ractor の間は shareable なものしか渡せないので、状態の隔離とイベントの不変性が言語の仕組みで守られる
- シャードが異常終了しても他は動き続け、検知して再起動できる

ただし、次のような場合は効果が小さくなります。

- **処理時間のほとんどがデータベース待ち**: CPU 並列の出番が少ない
- **Puma のマルチプロセス構成**: コアの活用はすでにプロセス側でできている
- **GC**: Ractor をまたいで全体が止まるので、アロケーションの多い処理では並列の伸びが頭打ちになる

Ractor が効くのは、イベントの再生や `handle` が CPU を使うワークロードで、1プロセスでコアを使い切りたい場合です。

## Rails の複数プロセスで同じ集約に書いても大丈夫？

大丈夫です。イベントの追記は楽観ロックつきで、別のプロセスが先に書いていたら、状態を読み直してコマンドを判定し直します。メモリ上のアクターは「単一ライターの保証」ではなく、「状態のキャッシュ + プロセス内の直列化」として働きます。

## イベントハンドラは必ず呼ばれる？

いいえ、at-most-once です。イベントを書いた直後にプロセスが落ちると、そのイベントはハンドラに届きません。読みモデルのように取りこぼせない用途では、[サンプルアプリの読みモデル](sample-app.html#読みモデル) のように、version を使って重複を無視し、欠落をイベントストアから埋めてください。

## `apply_event` を変えたら何に気をつける？

スナップショットは「その時点の `apply_event` で作った状態」なので、結果が変わる変更をしたら `snapshot_schema` を上げてください。古い番号のスナップショットは使われず、イベントの再生で作り直されます。イベント自体は不変なので、書き換えないでください。
