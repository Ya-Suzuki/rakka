# アクターと Ractor
{: .no_toc }

1. TOC
{:toc}

## 3つの層

Rakka では、次の3つを分けて考えます。

| 層 | 意味 | Rakka での実体 |
|---|---|---|
| 集約 | ドメインの単位（口座 123、出品 456 など） | `stream_id` で区別されるイベントの列 |
| アクター | 状態を持ち、メッセージを1件ずつ処理する論理的な単位 | シャード Ractor の中のエントリ（behavior + state + version） |
| 実行単位 | 実際に CPU の上でコードを動かすもの | シャード Ractor（コア数ぶん） |

**集約 = アクター** は1対1です。口座1つにつき、独立した状態・直列な処理・個別のクラッシュと復元があります。一方で **アクター : 実行単位** は多対少で、多数のアクターが少数のシャード Ractor に同居します。

## なぜ 1アクター = 1 Ractor にしないのか

Ractor は固有のスタックを持って並列に走る、重い実行単位です。集約の数だけ Ractor を作ると、集約が数千〜数万になったところでメモリが持ちません。

Erlang や Akka が数十万のアクターを扱えるのも、アクターを OS スレッドに1対1で割り当てていないからです。

| | アクターの実体 | 1個あたり | 実行するもの |
|---|---|---|---|
| Erlang | BEAM VM の軽量プロセス（独自のヒープとスタック） | 数KB | スケジューラスレッド（コア数） |
| Akka | オブジェクト + メールボックス（スタックなし） | 数百バイト | ディスパッチャのスレッドプール |
| Rakka | シャード内のエントリ | 約1KB | シャード Ractor（コア数） |

Ractor が担うのは、Erlang でいえばスケジューラスレッド、Akka でいえばディスパッチャの役割です。5万アクターを4シャードに載せたときの Ractor の数は6個（シャード4 + メイン + ストア）でした。

## Ractor を使う意味

アクターを Ractor にしなくても、Ractor にはまだ役割があります。

- **CPU の並列実行**: シャード同士は GVL に縛られず同時に動くので、`handle` / `apply_event`、復元時のイベント再生、JSON の変換が1プロセスの中で複数コアに乗る
- **隔離の強制**: Ractor の間は shareable なものしか渡せないので、「アクターの状態を外から触れない」「コマンドとイベントは不変」が規約ではなく言語の仕組みで守られる
- **障害の境界**: シャードが異常終了しても他のシャードは動き続け、`Ractor#monitor` で検知して再起動できる

逆に、処理時間のほとんどがデータベースの待ち時間なら、CPU 並列の効果は小さくなります。詳しくは [よくある疑問](../faq.html) を参照してください。

## ルーティング

アクターの置き場所（ホーム）は `crc32(stream_id) % shard_count` で決まります。同じ集約へのメッセージは必ず同じシャードに届くので、ロックなしで直列に処理されます。負荷が偏ったときは [リバランス](rebalancing.html) でホーム以外のシャードに移ることがあります。
