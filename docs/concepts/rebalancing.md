# リバランス
{: .no_toc }

1. TOC
{:toc}

## なぜ必要か

ハッシュでの割り当ては、アクターが多ければ均等になります。しかし忙しいアクターがたまたま同じシャードに集まると、そのシャードだけが詰まり、他のコアは空いたままになります。Rakka は溜まっているアクターを、メールボックスごと空いているシャードへ移します。

16個の CPU バウンドなアクターが全部同じシャードに当たったとき（4コア）:

| | 所要時間 | シャードごとの処理数 |
|---|---|---|
| リバランスなし | 4.8秒 | 800 / 0 / 0 / 0 |
| リバランスあり | 1.6秒 | 215 / 195 / 205 / 185 |

## いつ・どれを移すか

調整用の設定はありません（`rebalance: false` で無効にできるだけです）。各シャードが「メッセージ1件の処理時間」と「アクター1つの復元時間」を実測していて、次の条件をすべて満たすときだけ移します。

1. 最も忙しいシャードと最も空いているシャードの差が、移動の手間（復元時間を含む）より大きい
2. 移動先は、移動が済む頃には手が空いている（全シャードが忙しいときに移すと、手間のぶん全体が遅くなるだけ）
3. そのアクターを移しても、今のシャードで待つより早く終わる（1つのアクターに負荷が集中している場合は、移しても偏りが移るだけなので動かさない）

溜まり具合は件数ではなく、「捌き切るまでの見込み時間」（未処理数 × 1件の処理時間）で比べます。負荷を調べる間隔も、偏りがある間は 10ms、無ければ最大 0.5秒まで延びます。

## 順序を保つ引き継ぎ

移動中もアクターごとのメッセージ順序は保たれます。

1. 移動先に「これから引き継ぐ」と伝える。移動先は、引き継ぎが届くまでそのアクター宛てを保留する
2. ルートを切り替える。以降のメッセージは移動先に届き、保留される
3. 移動元はアクターを手放し、溜まっていたメッセージを移動先に渡す
4. 移動先は「引き継いだ分 → 保留していた分」の順でメールボックスに入れて、処理を再開する

状態そのものは運ばず、移動先がスナップショットとイベントから復元します。万一2つのシャードが同じアクターを処理しても、[楽観ロック](persistence.html#楽観ロック) が整合性を守ります。

```ruby
system.migrate("BankAccount-123", 2)   # 手動で移すこともできる
system.shard_index("BankAccount-123")  # => 2
```

{: .note }
リバランスはプロセスの中のシャード間だけで行います。プロセスをまたいだ移動はしません。
